# Перенос наработок из my_bible_app

`my_bible_app` закрывается как самостоятельный продукт. Его
наработки используются выборочно, а не копируются целиком. Источником истины для
данных остаётся Bible Desktop.

## Переносим как идеи и проверенные контракты

- production API client и типы Bible/профиля;
- схема персональной конфигурации версии 3;
- модель profile ID + secret + recovery code без обязательного аккаунта;
- PWA/Apache fallback и ориентация на Plesk Node.js 22;
- RU/DE-локализацию и mobile-first подход;
- доказанные сценарии чтения, закладок и офлайн-оболочки — по мере реализации
  соответствующих экранов.

Код адаптируется к Feature Registry и архитектуре нового проекта. Копирование
всего старого frontend создало бы две параллельные модели продукта.

## Не переносим

- отдельный бренд и домен Azbuka;
- старый onboarding как центр продукта;
- жёстко заданный набор разделов;
- отдельный backend или дублирование данных Bible Desktop;
- mock/fake-интеграции вместо production API;
- платформенные заготовки, пока для них нет подтверждённого продуктового этапа.

## Карта соответствий

| my_bible_app | Biblia App |
|---|---|
| Фиксированная конфигурация приложения | Композиция feature IDs |
| Azbuka Web App | Будущий `slavonic.learning` feature |
| Общий API client | `src/services/api` |
| Profile configuration v3 | `src/personal/configuration.ts` |
| Web PWA shell | Общий App Shell всех готовых и личных композиций |
| RU/DE словари | Единая локализация с выбором по домену |

## Порядок завершения старого проекта

1. Не добавлять туда новые продуктовые функции.
2. Переносить только то, для чего открыт конкретный этап Biblia App.
3. После переноса сравнивать контракт с текущим Bible Desktop API, а не со
   старым mock или snapshot.
4. Сохранять историю старого репозитория как справочную; не смешивать Git-
   историю двух проектов.
5. Архивировать старый repository только после отдельного решения владельца.
